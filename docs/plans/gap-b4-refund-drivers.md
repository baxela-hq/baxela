# Plan gap-B4 — Gateway refund coverage (Adyen, Checkout.com, Mercado Pago, Razorpay)

> **Purpose of this document:** Execution plan for Phase B task **B.4** of
> `docs/PLATFORM_GAPS_ROADMAP.md`. Goal: every enabled gateway except NowPayments can
> execute refunds through the existing two-phase ledger — honestly, including the
> gateways whose refund outcome only arrives asynchronously — and NowPayments'
> impossibility is stated plainly instead of hidden behind a generic message. All code
> facts verified 2026-11-07 against the current tree; provider facts verified the same
> day against official docs.
>
> **Created:** 2026-11-07 · **Owner:** solo maintainer · **Status:** **v2.2 — final
> review (9.2/10: "architecture approved; make the small corrections, then proceed")
> corrections folded in — approved for implementation** · **Size:** 4–6 focused
> implementation days across two landing stages (Stage 1: core wiring + Adyen +
> Checkout.com; Stage 2: Mercado Pago + Razorpay + NowPayments disclosure + docs) —
> plus an explicit buffer for provider sandbox testing and webhook troubleshooting.
> Implementation order per the final review: **core ledger infrastructure and its
> invariants land and are proven first; no driver is wired before that** (D11a).
>
> **Scope note vs the roadmap line:** the roadmap sketches "refund via their REST APIs
> (`Http::fake` tests, mirror the Stripe driver's two-phase refund flow)". Verification
> found the one-liner misses the hard parts, and two review rounds sharpened them into
> this plan's backbone: (1) the four link-based drivers **discard the gateway-side
> transaction id** every refund API keys on; (2) Adyen/Checkout.com/Razorpay refunds
> are **asynchronous** — 2xx means accepted, not completed — so the ledger gains
> `processing` and post-terminal `reversed` states with a complete transition matrix,
> and refund-outcome webhooks correlate by a merchant reference we control; (3) a
> gateway can reverse a refund after the fact — in either webhook order — and the
> accounting must follow atomically. The repo's driver-test convention is
> Mockery-mocked clients ("tests only ever mock this class"), not `Http::fake`; the
> plan follows the existing convention and adds `Http::fake` coverage only for the new
> client methods. Conventional commits; never commit unless asked.

## 2. Design decisions

| # | Decision | Why |
|---|---|---|
| D1 | **Four-identifier model, each with one meaning, never overloaded.** | Every refund API keys on an id we currently throw away; and webhook correlation must never depend on an id that isn't persisted yet (review 1.1/1.2/1.4, v2.1 §2.1/2.2). |
| D1a | **The four identifiers** (v2.1 — the ledger uuid is named explicitly; echoed reference and gateway refund id are **separate `WebhookResult` properties**, never one overloaded field): | |
| | \| Identifier \| Location \| Meaning \| | |
| | \|---\|---\|---\| | |
| | \| Internal payment match key \| `payment_payments.transaction_id` \| unchanged; what payment webhooks match on \| | |
| | \| Gateway payment ID \| `payment_payments.gateway_transaction_id` *(new, nullable, indexed at use-sites)* \| provider's payment identifier: Adyen pspReference, CKO `data.id`, MP payment id, Razorpay captured `pay_` id — persisted by the webhook settle path \| | |
| | \| Internal refund correlation ID \| `payment_refunds.uuid` \| Baxela uuid sent as the merchant reference on every refund call and echoed back on refund webhooks; also the idempotency key \| | |
| | \| Gateway refund ID \| `payment_refunds.transaction_id` \| provider's refund identifier (semantics unchanged since launch); for async rows written **at accept** rather than only at finalization, and indexed. The review's proposed `gateway_refund_id` column would duplicate it \| | |
| D1b | **Accept-response refund id per provider** (2.2): Adyen refund response's own reference (`id`/`pspReference` ⚠ verify exact field in the client test), CKO refund/action id (`action_id`/`id` ⚠ verify), Razorpay refund object `id`, MP refund object `id` — each client test asserts the real response shape; the payment id and refund id are never assumed interchangeable. **A missing refund id in the accept response is state-honest (final review §1.1):** a 2xx accept with no parseable refund id still means *accepted* → `processing` (reservation kept, warning-level diagnostic with the uuid; reconciliation then correlates via the echoed uuid — async gateways) or via a same-key retry (MP); a response too malformed/ambiguous to establish acceptance at all → `reconciliation_required` (reservation kept). **Never `pending` after a 2xx, never a fabricated id, never false success.** | Payment id ≠ refund id; assuming otherwise corrupts reconciliation; state names must track reality (final review §1.1). |
| D2 | **Honest async acceptance via a new `processing` state — with the complete transition matrix (v2.1).** Synchronous drivers (Stripe, PayPal, MP when the response refund object is terminal ⚠ verify MP status values) keep today's immediate finalization. Async drivers (Adyen, CKO, Razorpay) move the row `pending → processing` on a 2xx accept: the row keeps its reservation, stores the gateway refund id, fires **no** `PaymentRefundedEvent`. The definitive webhook moves it on per the matrix. **`success` keeps its meaning: definitively completed.** **Complete matrix** — every permitted transition tested, key forbidden ones asserted (`reversed→success`, `failed→*`, `success→failed`): | An uncertain refund must be neither definitively successful nor definitively unsuccessful; partial matrices invite illegal-by-accident transitions (review v2.1 §1.2). |
| D2a | **The matrix (final review §1.2/§1.3):** `pending → processing \| success \| failed \| reconciliation_required \| reversed` · `processing → success \| failed \| reversed` · `reconciliation_required → success \| failed \| reversed` *(the existing success/failed legs are the path a late webhook uses after a create-call timeout — now explicit; the `reversed` leg is D6b's no-accounting path, valid from all three pre-terminal states because a verified `REFUNDED_REVERSED` asserts the refund completed and was returned regardless of when the webhook lands — even before the accept HTTP response)* · `success → reversed` *(gateway reversed a completed refund — D6a restores accounting)* · `failed → ∅`, `reversed → ∅` *(terminal — a webhook contradicting an operator's resolution is reported for deliberate reconciliation, never auto-applied)*. | |
| D2b | **Stale `processing` rows are never auto-failed and reservations are never age-released (v2.1 §1.4).** A refund can legitimately stay provider-pending for days; marking it failed on age alone could let the merchant double-refund money already returned to the customer. Resolution always requires **operator verification of the provider's actual outcome** — the existing `ResolveRefundAction` discipline, extended to `processing` (admin surfaces stale rows for *investigation*, with the reservation note visible; no age threshold drives any automatic transition). A late webhook contradicting an operator's resolution hits a terminal row → reported loudly with identifiers (D3), reconciled manually — never auto-applied. | Review v2.1 §1.4. |
| D3 | **Refund-outcome webhooks correlate by the echoed ledger uuid — the accept-commit race is impossible by construction, no inbox table.** The refund request carries our uuid as the gateway's merchant reference (Adyen `reference`, CKO `reference`, Razorpay `notes.baxela_refund_uuid`); the providers echo it back on their refund webhooks (verified, §1). The ledger row is committed **before** the gateway call, so any webhook we caused can always resolve its row — there are no unmatched events for refunds we issued. (Deviation from the first review's preferred inbox: justified by the verified echo support on all three async gateways + MP being sync. The inbox is the **designated upgrade path** if a future gateway without reference echo is added — see §5.) **Validation chain before any finalization, in order:** signature verification first (existing mechanisms, unchanged — an invalid signature is rejected regardless of what it references); the echoed uuid resolves to a ledger row; payment association holds (where the provider carries the original payment id — e.g. Adyen `originalReference` — it must equal the payment's `gateway_transaction_id`); amount and currency agree with the ledger row where the payload carries them. **Any mismatch: never finalize** — reported at **error level with enough identifiers to investigate** (refund uuid, gateway refund id, expected vs received amount/currency — never raw sensitive payload data), then acked. Unknown uuids (dashboard-issued refunds) are logged as an **expected category at notice level**, kept distinguishable from validation failures. **Reversal-event correlation (final review §1.4):** the echo is verified for `REFUND`; `REFUND_FAILED` and `REFUNDED_REVERSED` must not be *assumed* to carry the uuid in the same field — at implementation, each event's sandbox payload is an explicit acceptance gate for its correlation field; the documented fallback is the **stored gateway refund id** (the event's refund psp vs `payment_refunds.transaction_id`, scoped by the original payment via `originalReference` vs `gateway_transaction_id`). A reversal is never associated with the wrong refund: when neither key resolves, the event is logged (notice) and acked, never guessed. Dedup: `canTransitionTo` is the invariant — duplicate, late or regressive deliveries are provable no-ops; provider event ids (CKO notification id) are logged where they exist. | Review 1.1 (durable, not probabilistic, handling), 1.4, 2.2, A, B; v2.1 §2.4; final review §1.4. |
| D4 | **Webhook boundary (v2.1 wording):** existing payment **matching and settlement behavior remain unchanged, except for the additive persistence of the provider-side payment identifier** (D1). Refund-outcome webhooks never settle payment rows, and payment-result webhooks never modify refund rows. | States the intended boundary literally, without the "byte-for-byte" overclaim. |
| D5 | **Idempotency on all four gateways (v1 corrected) + merchant-reference echo.** Every refund call sends the ledger row's uuid as its idempotency key: Adyen `Idempotency-Key`, CKO `Cko-Idempotency-Key`, MP `X-Idempotency-Key` (mandatory there since 2024-01), Razorpay `X-Refund-Idempotency`. Where the provider offers a merchant reference on the refund (Adyen, CKO) it also carries the uuid (correlation + gateway-dashboard debuggability); Razorpay gets it via `notes`. Ambiguous outcomes (timeout) are still **never retried blindly** — RECONCILIATION_REQUIRED for an operator, as today. | The `PaymentRefundInput.idempotency_key` contract is now honored by every wired gateway; verified against the refund endpoints specifically (review 2.5), not generalized from payment creation. |
| D6 | **Reversal in every webhook order, with atomic accounting restore (v2.1 §1.1/1.3 + final review §1.3).** New ledger state **`reversed`** (terminal; non-reserving — the amount becomes refundable again). **(a) `success → reversed`** — Adyen `REFUNDED_REVERSED`, or `REFUND_FAILED` on an already-`success` row (scheme decline after acceptance; on a pre-terminal row it is the ordinary `→ failed`): `ReverseRefundAction` runs in **one DB transaction** — lock the refund row, transition it, **recompute the order's refunded total from the ledger's success-only rows** (never subtract from the previous total), recalculate `refunded_amount` + payment status via the new **`OrderGatewayInterface::reverseRefund(orderId, refundedTotalMinor, paidTotalMinor)`** (which locks the order row; derives `paid` / `partially_refunded` / `refunded` from the sums; backed by **additive downward transitions** on `OrderPaymentStatusEnum` — `applyRefund()` itself keeps its forward-only invariant), commit atomically, and emit **`PaymentRefundReversedEvent` only after commit**. Idempotent under duplicate deliveries (row lock + transition guard); a mid-transaction failure rolls ledger and accounting back together. **(b) reversal of a never-finalized refund — `pending \| processing \| reconciliation_required → reversed`** (final review §1.3: the webhook can land while the accept response is still in flight, or after it timed out): a verified `REFUNDED_REVERSED` asserts by itself that the refund previously succeeded and was returned to the merchant, so it establishes the final `reversed` state **directly, with no refund accounting applied** (the refund was never active in Baxela's accounting) and the reservation released; the late success webhook / accept-path conditional update (still-pending only) then no-ops. Both orders tested per source state. | Review 1.3/2.6 + v2.1 §1.1 + final review §1.3: the accounting must follow the gateway in every delivery order, atomically, and never twice. |
| D7 | **Razorpay: persist the captured `pay_` id straight from the webhook.** `payment_link.paid` carries `payload.payment_link.payments.entity[]` — persist the captured payment id as `gateway_transaction_id` at settle; no extra `GET /v1/payment_links/{id}` at refund time (kept as documented fallback if the payload shape disappoints ⚠). **A link with multiple captured payments is never refunded arbitrarily** — refund() refuses explicitly and the admin resolves manually. | Review 2.4: no extra API dependency in the refund path; no arbitrary money movement. |
| D8 | **Mercado Pago is a sync driver; notifications reconcile per refund id; timeouts reconcile by evidence (v2.1 §1.5).** The POST response refund object decides the outcome (terminal → success; non-terminal ⚠ verify values → `processing`). Its payment notifications (`refunded`/`partially_refunded` statuses) serve only to reconcile stale `processing` rows: fetch the payment resource, walk `refunds[]`, match **individual refund ids** against stored gateway refund ids, validate amount, process only the matching refund — never finalize from the payment's blanket status. **Timeout scenario:** the response is lost after MP created the refund (row → `reconciliation_required`, no refund id): reconciliation fetches the payment's `refunds[]` and matches candidates by **amount** (+ currency, date window where needed) — exactly one candidate → operator confirms, row finalizes with that refund id; several equally-matching candidates → ambiguous, reservation kept, manual resolution — **never an arbitrary pick**. A same-key retry (`X-Idempotency-Key` = ledger uuid) is the operator's clean alternative (final review §2A): it **reuses the original ledger uuid — never a fresh key for the same refund attempt** — so MP's idempotency replay returns the originally created refund (supplying the missing id) instead of creating a second one; the implementation respects the provider's idempotency retention window and **never retries automatically or indefinitely** — the retry is an explicit operator action. Documented in payment-flow.md. | Review 2.3 + v2.1 §1.5 + final review §2A. |
| D9 | **NowPayments stays non-refundable, stated precisely (v2.1 §2.5).** No driver change (keeps `CannotRefund`). Admin copy branches on `method === 'nowpayments'` (method keys mirrored in the admin schema) and states exactly: **"Baxela cannot issue provider-side refunds for NowPayments payments. Any customer reimbursement must be arranged separately by the merchant."** — avoiding both the generic "not wired yet" (which promises a future that won't come) and any implication that the customer cannot be repaid at all. 6 locales. THIRD_PARTY_SERVICES row says provider-impossible (provider-side). | Roadmap decision; wording distinguishes platform limitation from merchant obligation. |
| D10 | **Legacy payments refuse explicitly.** Payments settled before the column ships have `gateway_transaction_id = NULL`; their drivers' refund() throws `refundNotSupported` (ledger records the FAILED attempt as today). The admin's honest path for those rows: manual refund in the gateway dashboard. | No backfill exists — the id was never stored; inventing a lookup that doesn't exist at the gateway would be worse. |
| D11 | **Two landing stages; core infrastructure lands before any driver** (review §3): Stage 1 = core wiring (D1–D6, D10) + Adyen + Checkout.com; Stage 2 = Mercado Pago + Razorpay + NowPayments disclosure (D9) + docs. Each stage updates the A.1 footnote wording, the THIRD_PARTY_SERVICES table, and the CHANGELOG. **D11a (final review):** within Stage 1, the core ledger infrastructure **and its tests** land and prove the transition matrix and accounting invariants *first* — no driver is wired before that. | "~2 drivers per release" staging, kept as commit-level staging; correctness infrastructure must exist before the first driver depends on it. |
| D12 | **API responses and UI distinguish acceptance from completion.** The create-refund response returns the ledger row (`processing` for async gateways) — the admin refund dialog gains one hint string: some gateways confirm asynchronously; the row shows *processing* until the gateway's webhook confirms. Refund-status labels gain `processing` and `reversed` (6 locales); the resolve dialog also offers resolution for stale `processing` rows (D2b discipline). | The ledger row is the truth surface; the UI explains it rather than inventing a parallel signal. |

## 4. Edge cases

- **Accept-commit race: impossible by construction** (D3) — webhooks correlate by the ledger uuid that is committed before the gateway call. The residual subtlety is the opposite ordering: the webhook confirms **or reverses** before the accept-path update runs — handled by the conditional (still-pending) update; the row keeps the webhook's outcome (tested).
- **Reversal before success, in any pre-terminal state** (D6b): from `pending` (webhook races the accept response), `processing`, or `reconciliation_required` (accept timed out) → directly `reversed`, no accounting applied; the late success / conditional accept-update is a logged no-op — never incorrect accounting (final review §1.3, tested per state).
- **Duplicate / late / regressive refund webhooks** → `canTransitionTo` guard acks; accounting applied once; a late success after `reversed` is a logged no-op, never a status regression. Concurrent same-row deliveries are serialized by the row lock + atomic transaction; thread-level parallel tests are deferred (§5).
- **Dashboard-issued refunds** (no ledger row) → ack + log (notice level); order accounting intentionally untouched — same as Stripe today; documented as a visible known divergence, not silently ignored.
- **Adyen `REFUND_FAILED` after `success`** → reversal path (D6a): accounting restored atomically, amount refundable again, event after commit.
- **Stale `processing` rows** → reservation held indefinitely; operator-verified resolution only; no age-based transition exists (D2b).
- **Razorpay link with several captured payments** → explicit refuse; never arbitrary (D7).
- **Razorpay unordered delivery**: `refund.processed` arriving after the create-call timed out resolves the `reconciliation_required` row (explicit matrix transition, D2a).
- **MP response lost after refund creation** → `reconciliation_required` reconciled by `refunds[]` amount-matching; ambiguous → manual; same-key retry returns the original refund (D8).
- **Legacy payments (NULL gateway id)** → explicit `payment.refund.not_supported`; ledger keeps the failed attempt; admin path is the dashboard (D10).
- **MP multiple partial refunds** → per-refund-id matching only; a notification never finalizes an arbitrary pending row (D8).
- **Response/webhook amount or currency mismatch** → never finalize; error-level report with identifiers + ack (D3).
- **Currency minor units**: Adyen/CKO/Razorpay integer minor units from `currency_decimal_places`; MP decimal — same boundary discipline as the existing drivers.
- **NowPayments**: no code path changes; text only.

## 5. Out of scope

- **Webhook inbox table** — the designated upgrade path if a future gateway lacks merchant-reference echo; unnecessary today (D3). Also no provider-event-id dedup table: ledger transitions are the invariant.
- Reconciling dashboard-issued refunds into the ledger (all gateways, incl. Stripe, today).
- True parallel-request concurrency tests (thread-level) — the reservation math is covered by overlapping-reservation tests; the phase-1 row lock is the mechanism, as today.
- Razorpay `speed: optimum` instant refunds — default normal only.
- CKO unreferenced refunds — referenced refunds only (we always hold the payment id after D1).
- Any NowPayments refund attempt — roadmap decision stands (crypto reversals are off-chain manual processes).
- Fixing the pre-existing retry behavior for other unmapped webhook events (e.g. Adyen CANCELLATION) — unchanged from today.
- Frontend/storefront refund surfaces — admin-only, as today.

## 7. Exit criteria (maps to Phase B's gate)

- Every paid order on Adyen, Checkout.com, Mercado Pago, Razorpay can be refunded (full or partial) from the admin, with the **definitive outcome** — not just the accept — reflected in the ledger and order accounting.
- A gateway-initiated refund reversal restores order accounting automatically and atomically — **in either webhook order** (success-then-reversal and reversal-before-success) — and re-opens the refundable balance.
- **`refunded_amount` always equals the sum of successful, non-reversed ledger entries** for the order (invariant under test).
- Duplicate, late and out-of-order refund webhooks are provably no-ops; signature-invalid ones are rejected before any correlation; stale `processing` rows keep their reservation until an operator verifies the provider outcome.
- NowPayments states plainly on both admin surfaces that **provider-side** refunds are impossible and reimbursements are the merchant's to arrange.
- A.1 footnote, THIRD_PARTY_SERVICES, payment-flow.md and the roadmap all describe the same reality as the `RefundableDriver` marker.
